# 第 21 章 Linux 开发环境

## 21.1 让代码、产物和记录各有位置

### 21.1.1 从一个项目目录开始

开发目录中常混有源代码、编译结果和运行日志。如果每次都在当前目录随意生成文件，很快会分不清该上传什么。建立一个小项目，主动区分这三类内容。

```bash
mkdir -p ~/linux-lab/dev/src
mkdir -p ~/linux-lab/dev/build
mkdir -p ~/linux-lab/dev/logs
cd ~/linux-lab/dev
```

src 保存源代码，build 保存可重新生成的构建结果，logs 保存运行记录。这些名称是本项目约定，不是 Linux 强制规则。发布时应能从固定源码和依赖重新生成产物，不能只靠某台电脑里一份来源不明的文件。

### 21.1.2 构建工具与运行时

编译器把源代码转换成另一种表示，运行时负责执行相应程序。对 Java，javac 编译 .java 为字节码，java 启动 Java 虚拟机运行它们。Maven 可以管理依赖、编译、测试和打包。这些工具需要版本记录，尤其在“本机能运行，服务器不能运行”时，版本与启动参数往往是最先要比对的信息。

## 21.2 用 Git 记录有意义的修改

### 21.2.1 本地仓库不等于公开发布

Git 是分布式版本控制工具，它的名字无需展开为一个技术缩写。git init 在当前目录建立本地仓库，git add 选择本次要记录的内容，git commit 形成一次提交。整个流程可以没有网络，也不会自动发布到 GitHub。

```bash
git init
printf '%s\n' 'build/' 'logs/' '*.class' > .gitignore
printf '%s\n' '# Linux lab project' > README.md
git status
git add README.md .gitignore
```

.gitignore 列出通常不应纳入版本记录的生成文件模式。已被跟踪的文件不会因为后来加入忽略规则就自动移除。密码、密钥和真实业务数据也不应提交。

### 21.2.2 配置自己的署名

提交需要作者名字和邮箱。使用你愿意记录到本地历史中的值，在本项目配置，避免不必要地改变全局配置。

```text
git config user.name "替换为你的名字"
git config user.email "替换为你的邮箱"
git commit -m "建立实验项目"
```

此处是需要替换的模板。提交信息说明发生了什么变化。之后修改 README.md，再运行 git diff 查看尚未暂存的差异；git diff --cached 查看已经暂存的内容。检查以后再提交，避免把临时调试信息一起保存。

## 21.3 可复现比依赖手工记忆更可靠

### 21.3.1 记录环境

项目说明中记录系统版本、架构、JDK 版本、构建命令与启动命令。依赖版本固定后，升级应作为明确变更处理。把网络下载脚本直接通过管道交给 Shell，会跳过阅读与校验，本书采用先检查来源与内容、再执行的方式。

### 21.3.2 把构建和部署分开

构建环境需要编译器与依赖，运行环境只需要执行应用所需的组件。初学阶段可以在虚拟机中完成两者，理解流程后再在本机构建并上传 JAR。服务器部署不应临时到任意目录寻找“最新那个 jar”，应使用明确的版本目录和文件名，第 24 章将把这一点变成操作步骤。

## 21.4 本章练习

- 不要往前翻｜源代码、构建产物和日志为什么分别管理？
- 命令填空｜查看未暂存差异使用 git ______。
- 看需求写命令｜仅把 README.md 加入下一次提交。
- 看命令猜结果｜git init 是否会自动在 GitHub 建立公开仓库？
- 找错误｜把私钥加入 Git 后再写进 .gitignore，能否自动从历史中消失？
- 无提示实操｜在专用项目里完成两次本地提交，第二次只修改说明文件，并查看历史与差异。

本章新命令为 git / 版本控制工具。首次接触的子命令有 init、status、add、commit、diff、config；查看历史使用 git log。复用 mkdir、printf，明天解释一次 add 与 commit 的差别。
